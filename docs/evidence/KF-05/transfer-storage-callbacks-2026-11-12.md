One owner holds two purchased NFTs and transfers one to a previously empty owner. Mock storage usage grew from 307200 to 307340 bytes, 140 bytes, while the sender's available prepaid credit stayed 966380000000000000000000 yoctoNEAR. At the captured 10^19 yocto/byte rate this increase corresponds to 1400000000000000000000 yoctoNEAR (0.0014 NEAR). These are host environment figures with short test account IDs and one transition, not deployed-Wasm, 64-character, upper-bound, or global-solvency evidence. The diagnostic intentionally asserts the pre-fix defect and must be replaced by correctness assertions when fixed.

The transfer entrypoints in `src/lib.rs` use `internal_transfer_unguarded` and do not charge account storage. The SDK's `near-contract-standards-5.30.1/src/non_fungible_token/core/core_impl.rs:166` modifies `owner_by_id`, per-owner `UnorderedSet` and the owner map, removing the old owner only if its last token moved and creating an owner set if needed. Thus a transfer can create persistent records when an existing owner keeps other NFTs; the measured example confirms this. The transfer-call additionally inserts `pending_transfers`; the resolver removes that marker and may recreate the previous owner's enumeration records. Other transactions between the tentative transfer and callback can change the owner sets, so using the initial net storage delta as an assumed rollback maximum is unsupported.

The callback currently requests up to `u64::MAX` bytes via `env::promise_result_checked` in `nft_resolve_transfer`. A large receiver result may consume callback resources; any bounded-read change must account for NEP-171 JSON boolean semantics, including legal whitespace, and demonstrate deployed receiver behavior. The current 50 TGas callback allocation has not been shown sufficient under adversarial state/results; no safe conclusion that callback failure is recoverable is available.

The remaining implementation must establish and test a bounded callback-storage reservation that cannot be spent by native withdrawal, account for payer attribution and released storage without crediting another user's backing, preserve arithmetic safety across concurrent deposits/pending withdrawals, and reserve enough callback gas before receiver execution. Actual receiver outcomes true, false, malformed, panic and reentry; 64-character identities and max purchase IDs; duplicate/private callback checks; exact liability reconciliation; host and deployed-Wasm tests; rebuilt candidate and funding sizing all remain NOT_RUN.
